## 推荐顺序与完成条件

### 阶段 41：MySQL 大结果读取与取消资源边界（优先）

本地已实现服务端N+1结果上限，1k/10k结果的真实驱动缓冲保持2/101行；详见[阶段41报告](stage-41.md)，待精确SHA远程双CI通过再标记完成。原普通游标可能先缓冲完整结果，`fetchmany(max_rows + 1)` 只限制取出的行数。先完成[阶段 41 具体计划](stage-41-plan.md)，再扩负载规模。交付真实 MySQL 大结果/慢结果回归、明确的读取边界、截断与空结果兼容、超时/取消后的会话和连接池清理证据。不能承诺数据库扫描量受返回行上限约束。

### 阶段 42：扩展并冻结 SQL 与检索验收集

沿用用户已选择的仓库合成 SQLite 数据，不等待业务数据。建立独立新版本，先补齐 **30 条 SQL 任务与 30 条检索问题**，按验收有效性再扩到各 120 条；数量是建设目标，不是已经具备的覆盖率。涵盖连接、聚合、否定、空集、NULL、时间边界、同名字段、无答案及库/领域过滤。每题写明输出列、排序、行语义和适用权限，标签独立推导并自检，加入可击穿错误 SQL/错误召回的反例。拆分开发集和保留集，不以待测模型输出直接生成 gold，不改旧版追分。

交付题集版本、输入摘要、标签来源、类别统计和 gold 自检报告；检索指标口径复用现有 Recall@K、Precision@K、MRR、nDCG。无业务标注时只能称合成验收集。脱敏业务集作为后续独立输入，不能捏造业务标签。

### 阶段 43：真实 embedding 与检索质量基线

依赖阶段 42 的冻结检索集。先复用现有 BM25 作为基线，再核验实际向量/混合检索及 Schema linking 进入生成上下文的路径；真实 provider 和模型版本需单独登记。比较相同文档、问题、过滤和 K 值下的排序指标，记录缺失/重复结果、无答案、跨库过滤、维度变化及索引重建失败。

交付真实 embedding 调用清单、缓存与索引身份、分层指标、耗时及缺测原因。准备阶段离线完成；联网或付费执行前提供调用次数、输入规模与资源上限，取得明确执行授权。只有同集对照证明收益后，才考虑新增重排器或语义缓存。

### 阶段 44：扩大真实 NL2SQL 端到端质量验收

依赖阶段 42；需要比较检索策略时再依赖阶段 43。现有受控模型工具只支持固定小集，先单独规划受限的新 profile 和批次预检，不能直接把 4 次上限取消。先跑 30 题冒烟，再决定是否扩到 120 题；每批在执行前列出精确 manifest、调用上限、输入/输出 token 参数、超时、重试及 fallback 策略。所有真实执行使用已冻结数据和 SELECT-only 账号。

交付生成完成率、验证/执行成功率、结果契约正确率、按题型错误、请求耗时、用量覆盖率和缺测；失败和缺预测均进入原定分母。同一固定计划下核对 JSON/SSE/MCP 的公共语义，费用未知仍为 null。比较模型或检索配置时固定题集、数据库和评分规则。原始问题/SQL/响应/凭据按隐私规则保留，公开报告脱敏。

### 阶段 45：大 Schema、混合负载与恢复测量

依赖阶段 41；测语义端到端负载时再使用阶段 43–44 的配置。先测 1k、10k 文档/对象量级，100k 必须先核定内存、磁盘和时间预算。分别测启动、Schema 刷新、查询与维护混合，以及并发 1/2/5/10；记录实际对象和文档数，不混称表数。

分开报告合成 Router 的编排容量和真实模型的端到端容量。观测事件循环滞后、RSS、磁盘、连接/任务数、排队、P50/P95/P99、拒绝率、取消后恢复；超时与 503 必须计入错误。先测基线，再针对已证实瓶颈优化并同环境复测。交付可重复工具、完整分母、故障后资源恢复证据及该环境的支持范围，不预设虚构吞吐/SLO。

### 阶段 46：持久恢复与进程一致性

先整理单 worker 模式的数据事实来源、重启顺序、备份恢复和持久化失败反馈。重点验证 RAG 索引未完成写入/补偿时的重启、设置落盘但未发布、会话与审计保留策略，避免重启后继续信任遗留索引。要求故障注入、明确降级、可操作恢复步骤和真实重启回归。

多 worker 暂不默认启用。若确有部署需求，先为会话/设置/连接注册表/索引所有权设计共享状态与失效协议，随后独立验收跨进程竞争和进程强杀；不能只增加 worker 参数后宣称支持。网络分区、TLS、数据库故障转移列为按实际部署拓扑执行的扩展场景。

### 阶段 47：类型债务、依赖与交付维护

可与阶段 42–46 穿插小批推进，不以集中大重构阻塞已授权验收。以现有 178 项类型诊断为初始证据，每批重新测量并按文件/错误码/消息比较新增与消除，优先真实执行、存储和公开接口；不关闭严格规则或用 Any 批量掩盖。最终目标是 `mypy app/` 全仓通过，未达到前持续公开剩余数量。

重新核验前端构建期依赖告警和 CI action 运行时提示，记录当前依赖快照与影响范围；在隔离分支逐项升级并跑构建/协议/双库回归，不沿用旧告警数作为当前审计结果。交付可复现安装、已处理风险和残余风险。依赖更新需要当时重新核对官方兼容资料，本文不指定未经验证的新版本。

### 阶段 48：发布前受限试用验收

汇总阶段 41–47 结果，冻结可支持的数据库/Schema 范围、单 worker 部署条件、账号权限、超时/资源预算和恢复指南。核对从干净环境部署、readiness、备份恢复、升级回退、审计访问与脱敏；以 gstack /browse 复验桌面/手机/键盘下的连接→查询→结果/失败→取消/重试→历史主路径。

交付发布检查单、支持/不支持清单和带已知限制的试用结论。实际发布与扩大访问面按当时用户授权执行。没有足够业务标签或容量数据时，试用结论必须保留这些缺口。

## 条件性后续，不抢占当前主线

- 生产账单对账、缓存/推理/阶梯/区域等复杂价格：需要供应商账单和价格版本；现有人工平坦单价估算已完成，不重复立项为缺失功能。
- 多租户细粒度对象隔离、共享会话/配置：需要明确部署与租户边界，不能把现有身份校验等同完整租户产品。
- PostgreSQL 跨 schema/search_path/临时对象、其他数据库方言、TLS/高可用：按支持范围逐项建真实环境；现有双库测试不替这些能力背书。
- 语义缓存、重排器、模型自动选择或更多 Agent 协作：仅在同集实验证明需求和收益后考虑；Harness 固定 YAML 顺序保持不变。

## 每阶段共同完成标准

先写计划和失败回归，再实现与验收；保持固定 YAML 节点顺序、setup→execute→update_context 生命周期、权限/只读、预算、三协议兼容、不串账不双计、未知不补零及取消释放资源。按改动运行定向及现有完整门禁，记录未运行场景。每阶段独立普通提交并上传 GitHub，核验精确 SHA 的两项 CI；文档补记提交也核验对应 CI。上传不自动等同生产发布或自动合并，后续合并依当时明确授权处理。

阶段 41 是当前唯一建议立即进入实施的阶段；阶段 42–48 是依赖关系和验收目标，执行前仍需各自形成具体计划，不在一个提交里实施全部路线。
