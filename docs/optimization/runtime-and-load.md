# 运行边界与本地负载验证

## 运行方式与边界

`python main.py` 使用 Settings.APP_HOST/APP_PORT（默认 0.0.0.0:8001），由 FastAPI lifespan 统一注册目录、初始化存储/认证/RAG/模型并关闭资源，不再由 main.py 先重复初始化。直接启动可用 `uvicorn app.api:create_app --factory --host 127.0.0.1 --port 8001 --workers 1 --limit-concurrency 64`。必须先配置随机 JWT_SECRET、邀请注册与管理员身份，见 security.md。

当前仍为单进程共享管理员工作台。连接、会话、目录和限流窗口在进程内；不能通过简单增加 workers 获得一致状态或全局限流。每条数据库原生连接由 serving loop 的独占 lease 管理；Schema 内省、查询执行和异步断开共享该边界。原生 SQLite（由工厂创建且允许跨线程）/DuckDB 的查询和内省转到线程，取消后 interrupt 并等待线程退出再释放连接。调用者自建、限制线程的 SQLite 保留同线程执行兼容性，不适合直接用于异步服务的长查询。

PostgreSQL/MySQL 暂时串行使用原有每库连接，未重构为请求级池；异步关闭会 await，MySQL 归还池连接后关闭池。真实服务器权限、事务/超时与断线恢复没有在本机验收。同步 close 仅保留给旧调用者；应用路径应 await aclose/aclose_all。MySQL 取消/超时会关闭连接，需管理员重连，未实现自动重连。

主 NL 查询最多 8 个执行槽，满时 JSON 503（QUERY_CAPACITY、Retry-After:1）；SSE 发送同名错误事件。120 秒请求截止覆盖排队/模型/工作流，JSON 504、SSE QUERY_TIMEOUT；基础设施失败没有 done，客户端不能推断成功。SSE 主动断连传播取消。直接 SQL 入口保留驱动级截止和连接排队，部署层须使用连接/并发上限；普通 HTTP 客户端断开不等于数据库已立即取消。不会自动重新提交失败查询。

模型工厂默认最多 4 并发、每 provider 60 次/分钟、单次 30 秒、1 次重试，失败冷却 5 秒后新请求可探测恢复。可通过 .env.example 对应 LLM_* 参数调整；max_retries 硬上限 3，请求级 YAML LLM 总预算仍生效。LiteLLM 的内部 num_retries 强制为 0，物理尝试由 Harness 计数。流式调用也持有并发槽和时限，但不在已输出部分文本后重放整个请求。限流/模型等待可取消；真实 provider 测试仍待外部凭据。

Schema 缓存默认 30 秒，返回深拷贝，显式刷新/重连/断开使缓存失效。统计和行数估计是快照；TTL 内外部 DDL 不会立即反映，且首次内省仍可能执行 COUNT。请求固定捕获配置/计划快照，复用加载器并检测文件时间变化，避免每请求重新解析 YAML。

进程内会话默认 1000 条、最近 50 轮、1 小时 TTL，创建/复用查询时清理；正在使用的会话不被容量清理，短期上限可额外容纳活跃请求。相同 session_id 的查询串行；不同 ID 不共享上下文。进程内版本最多 100 条，满后 409，不删除旧版本伪造成功。TTL 不删除持久化历史，也不是跨管理员私有会话机制。模型详细调用记录保留最近 1000 条，累计 token/费用/次数不随历史裁剪清零；价格表仍为估算，未知模型价格/流式 usage 不能作为账单。

`/health` 只表示进程存活；`/health/ready` 在初始化完成、认证可用、真实模型配置和至少一个登记数据库满足时 200，否则 503。RAG/存储状态单独显示；数据库仅检查登记状态，未运行 SQL 探活，不能冒充连续外部服务健康检测。

Trace 记录计划、状态、错误、节点时延和实际执行顺序；磁盘写入转到线程，失败日志和查询 warnings 可见。Runner 不再把输入全文/结果行写进节点摘要，但管理员 trace API 的 NL/SQL、异常文本仍可能含业务信息；生产应限制 data/traces 的访问并配置归档保留策略，不能将该目录推送仓库。后台索引任务在关闭时统一取消/等待，然后关闭数据库、子助手、存储、认证与 RAG。

## 已执行的实验

命令：`python -m scripts.load_test --requests 100 --rows 10000 --output docs/optimization/results/stage-4-load.json`。

Windows 11，Python 3.13.9，24 个逻辑 CPU，SQLite 3.51.0，httpx 0.28.1。单个内存 SQLite，facts 表 10000 条合成记录、10 个 bucket。每场景先 3 次预热，再按并发 1/2/5/10 各 100 请求：直接 SQL 与固定 SQL 的完整五节点流水线。实际 JWT 管理员认证、Schema/校验/执行启用；流水线显式使用 scripted router，不调用外部模型、不使用语义 RAG，不启动 MySQL/lifespan，不经过 TCP/TLS/反向代理。

这是短时间、本地 ASGI 实验，不能代表生产容量或稳定 P99。时延从客户端并发槽获准后计时，包含 ASGI 内部排队，不含外部负载发生器排队。报告同时输出全部请求与成功请求的分位数、成功/尝试吞吐、错误/状态分类、事件循环 lag P95、进程峰值 RSS、CPU 秒及按单核计算的 CPU 百分比。

最终一轮实际固定 SQL 流水线结果：

- 并发 1：100/100 正确，成功吞吐约 84.47/s；P50/P95/P99≈9.93/12.10/14.22ms。
- 并发 2：100/100 正确，成功吞吐约 95.22/s；P50/P95/P99≈19.82/26.59/30.00ms。
- 并发 5：100/100 正确，成功吞吐约 107.20/s；P50/P95/P99≈41.63/60.80/65.87ms。
- 并发 10：8/100 正确，92 次 503，拒绝率 92%；成功吞吐约 68.66/s。成功样本仅 8 个，P99 不具稳定统计意义。尝试吞吐约 858.29/s 大部分是快速拒绝，不能当作处理能力。

最终一轮进程峰值 RSS 约 233MiB（直接 SQL）/379MiB（加载 NLP 后流水线），CPU 约占一个核心，详细值见 JSON。不能由这一次短实验断言无内存泄漏或数据库/CPU已是生产瓶颈。

第一轮原始数据保留为 stage-4-load-before-cache.json。复用配置/计划加载器并完成末轮安全修复后复测，但直接 SQL（未涉及该缓存）也明显变快，证明存在显著环境噪声。两份记录的差异不是严格控制的消融实验，不给出缓存的稳定提升百分比；代码层确认消除了重复解析，量化收益仍需多轮独立验证。

## 生产压测前置与后续方案

准备脱敏 10万/100万行数据库快照，覆盖窄表聚合、带索引筛选、宽结果截断、复杂 JOIN、慢 SQL、冷热 Schema、同/多数据库、同/不同会话、取消与故障恢复。固定硬件、数据库角色、索引、连接/模型配置和数据版本。真实 RAG 准备 1千/1万文档并固定 embedding 模型、索引版本与标注查询；真实 LLM 先限定费用与 provider 配额。

逐层测：原生 SQL → API 直接执行 → 固定 SQL Harness → 真实模型/检索端到端。每层预热 30 秒、保持 60–180 秒、至少 3 轮，并发 1/2/5/10/20/50；上限要与 MAX_CONCURRENT_QUERIES 协调，超过上限单独分析拒绝率。使用 k6/Locust/外部 HTTP 发生器包含网络开销；增加 30 分钟稳态实验检测泄漏。记录成功吞吐、P50/P95/P99、503/504/业务错误率、正确结果率、队列等待、各节点时延、provider RPM/并发/token/费用、数据库活动会话/慢查询、CPU/RSS/线程/FD、事件循环 lag。SLO 与费用预算应由实际部署资源和业务要求制定，本阶段不虚构生产指标基线。

尚待验证：真实远程数据库/模型、长稳态、多进程、RAG 大规模同步索引对事件循环的影响，以及存储层故障与事务隔离。当前修复是 MVP 的有界运行与可测量起点，并非高并发架构完成声明。

## 阶段13：重连与进行中查询

resolve_query_targets在首次await之前捕获连接和info字段；Schema缓存仍按该句柄提取/深拷贝。query_service将同一来源对象的句柄传入固定Runner；ExecuteSQLNode在持有该句柄的lease后检查ConnectionFactory.is_current(db_id, connection)，避免等锁期间目标被替换后继续执行。aclose/替换原有流程继续等待原连接执行lease并使旧缓存失效；本阶段没有在LLM生成期间持有连接lease，也没有增加全请求全局锁。

重连可退休尚在生成中的旧请求：该请求失败且不能迁移，下一次显式请求重新提取新句柄Schema。多db_id目标独立，不因显示名称相同而合并；其他未变更目标可以继续。注册表只在单进程内，异步应用必须用await aclose/aclose_all；遗留同步close不能当作并发租约协议。直接修改注册表/原生连接、跨进程、应用外部切换USE/search_path/temp对象不在此次身份保证内。

验收使用SQLite/DuckDB真实驱动和确定性事件交错；没有复跑生产压测，不能将功能通过推断为吞吐/延迟提升。现有生产压测前置与指标方案不变。[阶段13记录](stage-13.md)。

## 阶段14：SQLite Schema版本与main读守卫

SQLite Schema提取前后读取main.schema_version，变化即拒绝混合快照；缓存命中前在lease内、通过既有native_call检查版本，不再等待TTL结束才发现DDL。执行和绑定EXPLAIN在worker内再次核对版本，旧请求失败而非自动迁移。旧的“DDL后必须invalidate前看不见新表”测试已改为版本变化即刷新，深拷贝和显式invalidate测试保留。

共享read_scope沿用只读动作集合，增加带版本查询的实际database=main读取要求；SQLite某些COUNT/索引优化回调database=None，因此安装守卫前读取main/temp表与视图名，缺失数据库名仅允许无temp同名遮蔽的main对象。其他数据库读取及未能证明的来源拒绝；绑定EXPLAIN不再降级为无守卫执行，结果最多1000条计划行。退出/异常时清理authorizer，原生结果路径继续清理进度处理器并恢复busy_timeout；取消仍等待worker退出后释放lease。

每次绑定读额外读取元数据，表数多时的开销是待测风险；本阶段没有吞吐/P50/P95/P99或生产容量结论。源版本不是数据/事务快照：检查后外部连接仍可发生DDL，不保证跨进程DDL与查询原子性；不可手工重置schema_version，仍以SQLite锁/编译/数据库权限为准。RAG索引不随缓存刷新自动重建，需要已有schema refresh入口并检查rag_indexed。其他方言、旧快照、直接SQL和对象授权限制见[阶段14报告](stage-14.md)。

## 阶段15：DuckDB解析状态与来源缓存

duckdb_source.source_state通过duckdb_databases/duckdb_schemas读取当前catalog/schema名及OID、当前search_path，并读取非internal的临时表/视图集合。OID用于识别同名namespace的替换，不是CREATE/ALTER TABLE版本。Schema内省前后及缓存命中前核对，命中仍要求TTL、句柄身份与深拷贝规则。执行/EXPLAIN在原生worker中再次核对；结果路径沿用计时中断/取消等待和lease，不在LLM生成期间持有连接锁。

当前只允许main且没有用户临时对象的绑定执行；这比仅检查同名temp更保守，避免猜测视图及多段标识符的内部解析。预存不支持环境和进行中状态变化分别返回source_scope_unsupported/schema_changed，均需用户显式新请求；不会自动USE或清理用户对象。DuckDB cursor()是独立会话，绑定EXPLAIN改用原句柄execute，最多1000条计划行，不回退到无守卫游标。

每次检查增加元数据读取，尚未进行大catalog/临时对象数量的性能评测；不能用全量pytest耗时比较吞吐/P95/P99。表列普通DDL、外部并发直接使用原生句柄、跨进程状态原子性、持久视图跨catalog引用和数据库权限不在此次保证内。临时对象集合变化有回归，但并非所有DDL都可被该状态感知；仍需已有refresh入口替换Schema/RAG索引，确认rag_indexed。详情及验证见[阶段15报告](stage-15.md)。

## 阶段16：显式刷新与索引提交

数据库层schema_refresh协调器按db_id使用单服务事件循环的gate，入口显式注入索引writer和文档转换函数，不依赖RAG引擎单例。它强制提取来源、使旧缓存失效；embedding在连接lease之外准备，在删除旧索引前重新内省并确认句柄/namespace/当前模型结构一致。忽略row_count_estimate/时间戳，正常DML不误判DDL。冲突再次失效缓存并返回409，用户显式新请求可获得新结构；没有给每个DuckDB查询新增全量表列扫描。

SchemaMetadataRAG同实例同db_id替换在准备与写入阶段串行，before_replace在embedding数量/维数检查之后、首次删除之前运行；空删除亦执行。其他库不必等待该库的embedding gate；这只是功能隔离，并非吞吐/SLO结论。普通低级upsert/clear及外部直接使用writer不自动获得已注册源校验，生产应使用共享入口。

人工/后台/启动/IndexRefresher四条来源路径均接入；IndexRefresher的成功时间/版本只在发布成功时更新，周期任务未默认启动。现有Schema内省仍可能执行COUNT估算，刷新时二次内省对大表成本待测；两个后端的同步写、外部进程DDL、跨进程锁/事务仍不提供原子性。普通DuckDB DDL仍需TTL/显式刷新，来源正确不等于索引与所有查询时刻严格一致。详情见[阶段16报告](stage-16.md)。

## 阶段17补充：Schema 索引故障恢复与运行边界

同实例同 db_id 的替换在既有 gate 内完成；两边快照准备成功后才删除，写失败分别同步恢复，恢复失败将该库隔离。检索在 embedding 等待前后核对，防止等待中失效后仍读取；健康库的指定检索独立可用。共享入口的 rag_indexed=false/warnings 是业务失败，应检查 previous index restored 与 recovery failed，不能将 HTTP200 当成功。后者先修复底层资源问题，再显式完整刷新该库，确认 rag_indexed=true；不要通过重启或直接查底层表绕过隔离。

此阶段没有持久恢复日志、多进程锁或跨系统事务。异常退出后需在开放持久索引检索前逐库全量刷新；备份需要与目标库索引量成正比的额外内存，快照/写/恢复均同步，生产阻塞程度未测。后续压测应增加大 Schema（1k/10k/100k文档）、正常刷新/故障补偿/查询混合场景，观测事件循环滞后、RSS峰值、磁盘 I/O、吞吐、P50/P95/P99与错误率；对100k先确认资源预算，不将单元测试耗时当容量结论。完整证据及限制见[阶段17报告](stage-17.md)。

## 阶段18：启动门禁与运行状态

初始化在事件循环gate中串行且幂等，候选引擎完成任务后才发布，异常/取消清理两后端句柄。每次启动完整枚举持久Schema所有者和当前连接库，标为待刷新后逐库验证；单库失败不会阻止健康库，未连接遗留内容继续隔离。get_schema_index_status只读进程状态，受保护status接口保留刷新器历史并提供当前列表，公开health/ready只给汇总计数。RAG可关键词降级，因此整体SQL就绪仍不强制RAG成功；存储/embedding并未被此接口实时探活。

应用已有10秒RAG初始化截止，同步所有者枚举/内省/写入不保证能被截止即时打断；大Schema或真实embedding可能导致整个候选取消并清理，再以RAG不可用运行。需要在独立容量测试中测启动耗时/事件循环滞后/RSS及超时后的句柄释放，不用本轮pytest耗时当性能提升。多进程、跨事件循环、在线热替换和持久事务日志尚未支持；手动恢复步骤与遗留库清理范围见[阶段18报告](stage-18.md)。

## 阶段19：按库维护顺序与取消

新按库clear先取schema-refresh外层gate，再取Schema RAG替换gate，复用空替换备份/补偿；成功后在外层gate内只失效目标刷新版本/时间。不获取源库lease，不调用源SQL/embedding；其他库可独立清理。取消排队不改数据，已开始的同步提交无await；较大索引的同步I/O/内存成本仍待测，测试10秒等待只是防挂起，不是SLO。

disconnect在关闭前标待刷新，关闭后按同一路径清索引；取消/失败不会继续信任遗留内容，响应分别表示连接已断开与索引清理结果。后续新刷新仍能重建，非永久tombstone。旧全量clear只支持明确有效scope或兼容默认all，拒绝query/未知字段，仍须维护窗口避免与在线刷新竞争；无引擎/损坏文件按离线运维处理。API和实测证据见[阶段19报告](stage-19.md)。

## 阶段20：工作台操作与读取顺序

工作台RAG维护使用即时ref防重复，同页批量/按库操作互斥；结束读取stats/status/databases，GET序号防旧响应覆盖结果，不轮询、不自动重试POST。读取失败仅禁用维护和给出重试读取入口，不伪造0条/无连接；定向清理按库确认，全量维护仍要求维护窗口，其他客户端/进程的竞争限制不变。

## 阶段21：本地前端交付

## 阶段22：配置发布与在途检索

设置GET/PUT及引擎构建共用当前loop的rag-settings gate；存储读/写各有10秒await截止，等待gate的时间不包含其中，不作为总响应SLO。写入成功后无await同步发布三个新融合器与内存；每次检索在首次await前捕获引用，保留自身快照，不锁住查询去等待配置存储。完整查询的多次检索调用没有统一配置版本，多worker无广播；取消可能已落盘但未发布，先读漂移再显式保存。源数据/索引不因调权重而重建。真实MySQL、跨进程竞争和同步驱动超时仍需独立环境验证，不能用此次测试耗时推断性能。操作见[配置契约](rag-settings.md)。
