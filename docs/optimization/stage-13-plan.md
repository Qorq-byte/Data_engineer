# 阶段13计划：固定查询来源与拒绝过期连接

基准15e51b2，代码及文档CI成功；继续codex/mvp-hardening独立工作树，不动原工作区或既有未跟踪文件。计划先于实现。

## 依据与取舍

query_service先通过_resolve_all_schemas提取Schema，后续runner.run却重新ConnectionFactory.get(db_id)；单库解析还会在内省之后重新取info。重连可能混合旧Schema、新方言/连接，并在同名表上返回错误数据库的答案。Schema缓存按句柄区分且关闭时失效，问题是请求消费时丢失来源，不应通过关闭缓存、全请求数据库锁或改写SQL解决。

本阶段固定每个目标的原生句柄/元数据/Schema，执行时在现有连接lease内确认注册身份；已替换或删除则失败。已有元数据辅助函数保留原返回契约；统一服务使用明确的ResolvedQueryTarget。LLM阶段不占数据库执行锁，Harness固定计划和节点生命周期不变。

## 顺序、验收和交付

1. 新增共享来源解析，先同步捕获句柄和info，再从该句柄内省；返回不可变目标结构。原_schema/_all_schemas辅助函数用适配器保留旧结构，修正过时注释。
2. query_service从这些目标建立Schema列表，runner始终使用目标原句柄，禁止后续按同db_id重新解析。ExecuteSQLNode持有lease后核对context.db_id与原句柄，变化返回明确connection_changed失败，不能读取新库或回退重试。无db_id的调用者自管连接保持既有行为。
3. 新增真实SQLite两库同Schema不同数据、重连/断开/连接info变化/跨目标隔离测试；验证三协议共同失败、正常重连后的新请求成功、原SQL及固定节点顺序不变。用确定性事件/回调控制交错，不以任意sleep制造竞态。
4. 定向及全量pytest、全仓Ruff、前端编译、核心strict（纳入新来源模块）通过；全仓mypy与197项基线对比，保留存量失败且无新增诊断。验证Schema缓存按旧句柄失效、新句柄重新提取。
5. 更新查询契约/运行说明/阶段报告/进度和结果证据；审查暂存范围及凭据，commit、普通push、核对远程SHA和Linux CI，补记远程证据。当前阶段达到验收后再进入下一阶段。

## 边界

不自动重试、不迁移进行中的请求、不延迟重连直到LLM完成，不将旧句柄当作可继续使用的快照数据库。此阶段不解决同一句柄上由应用外部执行USE/search_path/temp DDL导致的解析变化、跨进程注册表、对象级授权、生产容量或外部PG/MySQL网络行为；只读/超时/预算不削弱。
