# 阶段18计划：持久 Schema 索引启动验证与失败可见性

2026-10-22，基准836d83e及成功CI，继续独立工作树 codex/mvp-hardening。用户授权先规划后实施，沿用 brainstorming 方案比较与文件化阶段记录；原工作区和既有未跟踪文件保持不动。

## 已确认问题与方案

engine.initialize_rag_engine 在启动索引完成前赋值 _engine，逐库刷新结果被 suppress；持久索引重新构造后不保留阶段17隔离，旧内容未经本次启动来源校验即可读取。health/ready 的 rag 布尔值是启动时快照，learning/rag/status 只有刷新器启发式时间，没有真实 Schema 隔离状态。

选择启动重新验证：单例发布延后，持久库ID和当前连接库先标记待刷新，成功的完整替换才解除。相比只加状态接口，该方案阻止旧数据绕过；相比跨存储持久事务日志，改动适合 MVP。不增加多进程能力或默认后台定时任务。

## 实施顺序与验收

1. 两存储提供完整的Schema数据库ID枚举（包括仅存在一侧的记录），缺失/非法db_id应使初始化失败，不能默默认领。SchemaMetadataRAG增加待刷新状态，与写后恢复失败状态分别表示；指定库和无范围检索（含embedding等待后）均检查。局部upsert/其他库刷新不能解除，完整替换/删除/清空成功才解除。
2. 初始化在既有事件循环 gate 内串行并幂等；用局部 candidate 完成构造、标记及启动任务后才发布 _engine。异常/取消均清理候选资源，不发布半成品；getter 在初始化中继续拒绝。启动逐库结果记录成功/失败，固定日志避免原始错误泄漏，其他库继续初始化。已断开持久库保留待刷新，不能被无范围检索读取。
3. 受保护 learning/rag/status 保留既有刷新器字段，补充实际 Schema 待刷新/恢复失败列表及降级状态；初始化不可用时只返回固定消息。health/ready 动态读取进程内RAG状态，只暴露计数，不暴露库ID/路径；RAG可降级，整体SQL就绪仍沿用auth/真实LLM/连接的既有条件，不伪造后端或模型探活。
4. 先用真实持久LanceDB/FTS5重开证明旧索引未经验证可读，再覆盖两侧孤立记录/待刷新、启动成功/失败、显式刷新恢复、等待期间状态变化、取消/异常资源清理、并发初始化只建一次、状态API权限/脱敏和动态就绪。不弱化阶段17及Harness安全回归。
5. 定向/全量pytest、Ruff、前端、既有strict34源文件通过；全仓mypy与197项/42文件基线按文件/错误码/消息多重集比较，无新增诊断。不用单元测试耗时推断生产延迟/召回质量。
6. 更新计划/报告/进度、查询契约与运行/RAG说明及结果证据；审查暂存/凭据，提交并普通推送，核对远程SHA/CI，补记远程验收并推送文档。不强推/不合并main。

## 限制

这是每次引擎初始化的信任门禁，不是持久故障日志或原子快照；同一次运行中外部进程直接损坏索引、失效原生连接等不能靠状态判断。默认单进程单事件循环，来源校验限于现有模型；其他RAG namespace、真实embedding/PG/MySQL/生产容量仍待独立验证。启动有10秒应用截止，过大索引可能超时后降级，需要实测；同步存储扫描不承诺可被异步截止即时打断。
