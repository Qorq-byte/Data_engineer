## 现状与取舍

阶段18将持久遗留库隔离，但现有HTTP只能scope=schema全量清空；旧clear忽略db_id和未知scope，误用可能删除全部或假成功。disconnect_database还直接同步remove_database并吞失败，未受刷新顺序/补偿保护。优先提供按库操作闭环，避免引入批量任务框架/持久tombstone/全局重构。

## 顺序、范围与验收

1. 新增纯dataclass清理结果；SchemaMetadataRAG异步clear_database(db_id)复用空替换和双后端原始记录补偿，返回目标库真实删除数量，同实例同库替换gate保护。失败不得清理待刷新/恢复失败标记；成功清理才能解除目标状态，未知ID幂等0条。同步remove_database保留低级兼容边界。
2. 在数据库层增加清理协调函数，复用schema-refresh同库gate，成功回调只失效目标库IndexRefresher版本/时间缓存，不改其他库/进行中pending或历史startup结果。不要求原数据库仍连接，不执行SQL/LLM。遵循既有外层刷新→内层替换锁顺序，取消等待不改数据。
3. 新增管理员受保护POST /api/v1/learning/rag/schema/{db_id}/clear；无可选db_id默认，不可能退化为全量。成功返回scope/schema、db_id与removed计数；无引擎/准备或写失败为固定HTTP503/code，补偿结果可见但不泄漏原始后端异常。旧全量clear对db_id误用、未知scope返回422并在删除前拒绝，正常旧调用保持。
4. 断开连接后使用同一清理协调；连接断开结果与索引清理结果分别返回，失败有固定warning，不吞掉。索引失败可由新入口对已断开db_id重试；不在本阶段改变连接注册/授权模型。
5. 先写HTTP回归证明旧实现无按库入口且忽略db_id误清全部，再覆盖真实LanceDB/FTS5下目标/其他库与文档指标隔离、两侧单独存在、计数/幂等、写失败/恢复失败/准备失败、显式重试、同库刷新双向顺序/取消/其他库独立、401/403、引号标识、遗留库重启与断开入口。保留核心Harness与只读回归。
6. 定向/全量pytest、Ruff、前端、strict34源文件通过；全仓mypy对197项/42文件基线无新增诊断。更新计划/报告/进度/协议/运维与证据，暂存及凭据检查后commit/普通push，核对远程SHA/Linux CI，再补记并推送文档。不得强推或合并main。

## 边界

只覆盖Schema单库清理，不清原始数据库或其他namespace。全量clear仍是维护窗口操作，不承诺与逐库刷新事务隔离；同事件循环/同实例，外部进程/直接底层写/崩溃恢复不保证。清理时刻之后的新刷新可重新建索引，不是永久禁用该库。没有新增UI或性能/语义质量结论。无法读出持久索引导致引擎未初始化时，新接口503，需要已有离线备份/重建运维方式，不自动删损坏文件。
