# 阶段 41 计划：MySQL 大结果读取与取消资源边界

状态：**已实施，代码SHA本地及远程双CI验收通过；文档补记提交另核验最终SHA**。2026-10-26，基线 main `fecb7b9`，承接[阶段 40](stage-40.md)和[剩余路线](post-stage-40-roadmap.md)。本计划不产生模型调用或业务数据库访问。实施结果见[阶段41报告](stage-41.md)。

## 问题与范围

`ExecuteSQLNode._execute_aiomysql()` 当前调用普通 `conn.cursor()`，执行原 SQL 后才 `fetchmany(max_rows + 1)`。这限制响应行数，不能保证驱动未缓冲完整结果；只测返回 1 行不足以证明大结果资源有界。阶段 40 已确认正常功能和取消收尾，本阶段补齐读取规模证据，保留它们的兼容性。

目标是给应用侧结果读取建立明确行数边界，并验证超时、截断、取消后的游标/连接/池归还。行数边界不等于字节边界、数据库扫描/排序成本边界；本阶段不承诺任意大单元格或大 JOIN 的整体内存/服务端工作量上限。

## 方案与决策门槛

优先验证为受支持的只读查询增加安全的服务端结果上限，使结果最多返回 `max_rows + 1` 行，保留一行截断证据。适配已有 LIMIT、CTE、UNION、ORDER BY、结尾分号和合法注释，遵循现有 SQL 解析/只读边界；不能通过简单字符串拼接破坏语法或改变原有更小上限。EXPLAIN 使用独立路径，不将普通 SELECT 包装盲目套在计划语句上。

同时评估未缓冲游标：其关闭可能继续排空未读数据，取消后会话也可能不可复用，因此不能仅把游标类替换为 SSCursor 就宣布完成。第三种选择是保持普通游标并仅记录风险，无法满足本阶段的实际读取目标。先用失败回归与真实服务探针验证前两种方式，选择语义完整且能证明收尾的最小改动；如存在不支持的合法查询形式，明确失败或另定兼容策略，不静默无界回退。具体选择与拒绝范围在实现报告登记。

## 实施顺序

1. **建立失败证据。** 在阶段 40 专用 MySQL 容器和 SELECT-only 账号上，准备 1k/10k 行固定小列 fixture，`max_rows=1/100`。核对响应与真实驱动读取/缓冲规模；必须有能区分“返回行数限制”和“读取限制”的断言。使用稳定的驱动观测或结构化计数，不靠一次 RSS 差值决定功能通过。再补原 SQL 自带 LIMIT、复杂只读表达式和 EXPLAIN 兼容回归。
2. **实现有界读取。** 只调整必要的 MySQL 执行路径及共用安全辅助函数；继续由 Harness 决定节点顺序。保留列名、空结果、NULL/Decimal、row_count、truncated 及全局 max_result_rows 语义。非法/写入 SQL 仍在既有闸门拒绝。
3. **验证收尾。** 测截断后再查询、取消发生在执行/读取/关闭阶段、超时、连接重用或显式废弃、EXPLAIN sql_notes 恢复。用实际锁/事件控制交错，不仅依赖 sleep。不可恢复的会话从池移除，取消完成后无本阶段遗留任务或租约；清理失败不能伪造成功。
4. **检查协议及回归。** 在现有固定 Harness 和确定性 Router 下验证正常/截断/取消的公共输出，确保 JSON/SSE/MCP 不改变完成状态、用量与候选身份；不要求三协议传输帧逐字节相同。运行离线全量、两库真实套件、Ruff、配置的 strict 门禁、182 项既有前端契约和完整构建。若前端契约数量变化，说明原因，不把旧数字写成实测新结果。全仓类型债务新增为零。
5. **交付。** 更新执行边界文档、阶段报告和路线状态，记录容器/驱动版本、fixture规模、读取证据、失败回归及清理。独立分支普通提交推送，核验该 SHA 的 MVP 和真实数据库 CI；补记文档后再次核验最终 SHA。阶段 41 未完成前不修改总表为已验收。

## 验收标准

- 1k/10k 行结果在固定小列 fixture 下，真实驱动证据证明读取最多 `max_rows + 1` 行；结果规模扩大不使客户端缓冲行数随表总行数扩大。实验不等于任意行宽的内存上限。
- 0、恰好 N、N+1 及远超 N 的结果具有正确列名、返回行数和 truncated 标记；原有 LIMIT、排序、CTE/UNION 和 SELECT-only 权限保持。
- 超时/取消/关闭后，连接可安全重用或已明确移除；无仍占用池的失效会话，清理在测试截止内结束。截止/容差在运行前登记，超出则失败，不在看过结果后放宽。
- EXPLAIN 不泄漏优化器 SQL 备注；sql_notes 已恢复，恢复失败则会话废弃。普通 SELECT 不因该控制多出不必要的设置副作用。
- PostgreSQL 与现有 SQLite/DuckDB 路径不回归；不新增 LLM/embedding 调用、不改变未知费用、不放宽 Harness/权限/预算。

## 资源与排除范围

复用专用临时容器工具的环回随机端口、随机所有权标签、CPU/内存/tmpfs 限制与完整 ID 核验后清理。只使用合成 fixture，不连接宿主已有 MySQL，不挂载业务数据。先用 10k 行验证边界；如需更大实验，先登记资源预算。

本阶段不实施持久化 Schema 重构、不升级全部依赖、不建设多 worker 状态服务、不做真实模型评测或生产压测。不宣称服务器立即停止工作；服务端扫描量、宽行字节上限、网络分区/高可用和生产容量进入后续独立验收。
