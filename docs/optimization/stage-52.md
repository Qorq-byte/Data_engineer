# 阶段52：关键词 Schema 链接不再逐候选重扫全库

2026-11-01。阶段51 把 token 估算、Schema 校验和快照克隆移出了热路径，当时的记录里还留着一条"关键词检索仍是 O(表数) 全扫，10k 约 0.9 s"——那句话是**估计，没有测量**。本阶段先测，再改。

结论：`SchemaLinkingNode` 单次执行 **1k 表 48.8 → 7.7 ms（6.3×）、10k 表 548.9 → 124.6 ms（4.4×）**，10k 的 pipeline retrieve 阶段 **877 → 569 ms（-35%）**。行为不变，并且用差分测试对旧实现逐条比对过。

证据见 [stage-52-retrieval.json](results/stage-52-retrieval.json)。

## 1. 先测：0.9 s 是错的，但错的不是量级

两个容易被混在一起的东西：

| 测的东西 | 1k | 10k |
|---|---|---|
| `SchemaRetriever.retrieve()`（`keyword_retrieve` 场景，纯检索器） | 0.86 ms | 10.1 ms |
| `SchemaLinkingNode.execute()`（pipeline 的 link 节点，含 Phase-2 回退） | 48.8 ms | 548.9 ms |
| pipeline 里 `retrieve` 阶段（node_event 上报的节点耗时） | — | 877 ms |

所以"约 0.9 s"这个数**碰巧**接近 10k 的 retrieve 阶段（877 ms），但组成完全不同：真正的名字匹配扫描约 490 ms，其余是过滤 Schema、外键扩展与载荷组装。检索器本身只要 10 ms——它从来不是问题。

`cProfile` 抓 3 次 `execute`（1k）：

| 函数 | tottime | 调用次数 |
|---|---|---|
| `_all_column_matches` | 0.25 s | 114 |
| `str.lower` | 0.14 s | 1 716 198 |
| `_all_table_matches` | 0.044 s | 114 |

114 次 = 38 个候选 × 3 次执行，每次都在 1000 张表 × 12 列上重新 `lower()` 一遍。10k 下 3 次执行 1810 万次函数调用，全部是同一个模式的重复。

## 2. 改法：一次线性建索引，之后全走字典与 C 级扫描

新增 `app/knowledge/schema_name_index.py`：每次请求建一次索引（表名、列名、注释、名字分段），四条规则改成查表回答。

- **精确 / 大小写不敏感**：字典直达。
- **"候选是名字的子串"（0.65）**：把所有唯一的列名拼成一个大字符串，用 `str.find` 在 C 层扫一遍，命中位置用 `bisect` 反查是哪个名字；表名同理。
- **"名字是候选的子串"（0.6）**：候选本身很短，枚举它的所有子串去字典里查，比遍历两万个列名快几个数量级。
- **注释包含**：注释很少，保留线性扫描。
- **反查表名（`_scan_table_names_reverse`）**：原来是"每张表的每个分段 × 查询词"，改成反方向——先算出哪些分段能匹配（词表只有几百个），再并集出表。
- **直接关键词回退（`_direct_keyword_scan`）**：同样走索引，语义不变（没有表名命中就返回空，表示该查询与这个库无关）。

置信度、阈值、排序一律没动。因为四条规则的置信度**严格递减**（1.0 > 0.95 > 0.75 > 0.65 > 0.6），"每个名字取最高置信度"等价于原来的 `if/elif` 链；排序保持"置信度降序，同分按 Schema 顺序"。

两个边界是写测试才发现的：

- **阈值 0.0**：旧实现会把所有表/列以 0.0 分返回（`conf >= 0.0` 恒真）。索引按需补全了这一行为，否则调用方拿不到完整排名。
- **空候选**：`"" in s` 恒真，旧实现会给所有名字 0.65。同样保留。

## 3. 差分测试：不是"看起来一样"

`tests/test_knowledge/test_schema_name_index.py`（46 项）里保留了一份**旧循环的逐字复刻**，然后用随机 Schema（20 个真实风格表名、15 个列名、含大写与连字符、含中英文注释）× 随机候选 × 9 个阈值 × 8 条查询，逐条比对两个实现的返回值**和顺序**：

| 比对项 | 覆盖 |
|---|---|
| 表匹配 | 12 个种子 × 9 阈值 |
| 列匹配 | 12 个种子 × 9 阈值 |
| 反查表名 | 8 个种子 × 8 查询 |
| 直接关键词回退 | 8 个种子 × 8 查询 |

另有 6 项具名用例：索引复用结果稳定、置信度优先于 Schema 顺序、注释大小写折叠、短于 3 字符的分段不参与反查、空候选、构造索引不改动快照内容。

## 4. 前后对比

同一台机器、同一份夹具规格、`git stash` 切源码，背靠背跑。

**节点级（cProfile 同一脚本）**

| 规模 | 改前 | 改后 | 变化 |
|---|---|---|---|
| 1k 表 | 48.8 ms | **7.7 ms** | 6.3× |
| 10k 表 | 548.9 ms | **124.6 ms** | 4.4× |
| 3 次执行函数调用（10k） | 18 125 257 | **3 145 621** | 5.8× 更少 |

**pipeline 级（`scripts/scale_load`，pipeline 场景）**

| 规模 | 指标 | 改前 | 改后 |
|---|---|---|---|
| 1k 表（15 请求） | P50 | 267 ms | **126 ms** |
| | rps | 3.42 | **6.74** |
| 10k 表（6 请求） | total P50 | 3059 ms | 2867 ms |
| | retrieve 阶段 | 877 ms | **569 ms** |

10k 的总耗时只降了 192 ms，比 retrieve 阶段的 308 ms 少——因为 generate/validate/execute 两次运行之间本身就有 ±90 ms 的抖动（同一份代码），总差值落在噪声里。**能拿出来说的是 retrieve 阶段的 877 → 569 ms**，不是总耗时。

还有一条必须写下来的：**跨会话的绝对值不可比**。同一台机器上，阶段51 记录的 10k pipeline 是 1307 ms，本阶段同一份未改动的代码测出 3059 ms。这是机器状态差异，不是回归。所以本阶段只用**同会话背靠背**的前后对比作为证据，不拿它和阶段51 的数字直接相减。

## 5. 还剩什么

- **索引仍然每请求重建一次**：10k 下建索引 123 ms，正好是节点剩余时间的全部。它是"线性但只扫一遍"，比原来的"每候选一遍"好得多，但没消失。要再往下走，得让索引跨请求存活，而这需要先回答"Schema 什么时候真的变了"——不是本阶段能顺手解决的。
- **retrieve 阶段剩下的 444 ms**：`_build_filtered_schema`、`_filter_schema`、外键扩展、载荷组装。现在有具体归属了，下一轮可以逐个量。
- **合成词表不代表真实仓库**：夹具里 1000 张表的列名基本重复，唯一名字只有十几个；真实 10k 表仓库的唯一名字会多得多，0.65/0.6 两条规则的成本结构会不一样。
- 只测了 SQLite；差分测试证明的是"与旧实现等价"，**不是"旧规则排序合理"**。
